# 1. Project Overview — What Are We Building?

We are upgrading an existing exam portal into a multi-tenant SaaS MCQ examination platform.

The platform owner (Super Master) can create and manage multiple institutes.

Each institute gets its own:
- Institute name and URL/slug.
- Institute Admin account.
- Admin login.
- Database configuration.
- Subdomain/custom domain configuration.
- Email configuration using Resend.
- Payment configuration using Razorpay.
- Exams, questions, students and results.

### Our intended example

We are using three institutes for demonstration:

- Institute-1
- Institute-2
- Institute-3

Later, we can create unlimited institutes depending on the platform's capacity.

### Main workflow

Super Master Login  
↓  
Super Master Dashboard  
↓  
Select Institute-1  
↓  
Manage Institute-1  
↓  
Institute-1 Admin Login  
↓  
Institute-1 Admin Dashboard  
↓  
Create exams and add questions  
↓  
Generate examination link  
↓  
Students open the link  
↓  
Students take the exam  
↓  
Admin checks submissions and results

**Important:** Company-1 was our initial demo tenant. We renamed it to Institute-1 to match the actual business model.

# 3. SaaS Architecture — Our Agreed Design

We are planning a multi-tenant architecture with a central Control Plane and physically isolated tenant databases.

## Level 1 — Super Master

The platform owner controls the entire SaaS.

Responsibilities:
- Create institutes.
- Rename institutes.
- Manage institute status.
- Manage subscription plans.
- Manage institute Admin accounts.
- Reset Admin passwords.
- Configure tenant database connections.
- Configure subdomains and custom domains.
- Configure email integration.
- Configure Razorpay.
- Monitor institute activity.

Super Master credentials are managed through environment configuration.

Super Master must not need an account inside every institute database.

## Level 2 — Institute Admin

Each institute has its own Admin account.

For example:
- Institute-1 Admin
- Institute-2 Admin
- Institute-3 Admin

Responsibilities:
- Manage exams.
- Add and edit questions.
- Publish exams.
- Generate examination links.
- Manage students.
- Review submissions.
- View examination results.

An Institute Admin must only access their own institute's data.

## Level 3 — Students

Students use the exam links generated by their institute.

Responsibilities:
- Open exam links.
- Register or sign in where required.
- Attempt examinations.
- Submit answers.
- View results according to the examination rules.

We are not adding unnecessary staff roles at this stage.

# 4. Database Architecture — Important Future Design

Our intended architecture:

### Control Plane Database

The existing Neon database is currently being used by the application and contains the original monolithic schema.

The planned Control Plane responsibilities are:
- Tenant registry.
- Tenant name and slug.
- Tenant status.
- Subscription metadata.
- Encrypted tenant database credentials.
- Domain configuration.
- Provisioning information.

### Separate Tenant Databases

Each institute should eventually have its own PostgreSQL database.

Example:

- Institute-1 → Neon Database 1
- Institute-2 → Neon Database 2
- Institute-3 → Neon Database 3

Each tenant database contains institute-owned information:
- Admin users.
- Students.
- Exams.
- Questions.
- Results.
- Other institute-specific records.

**Important architecture status:**

Physical database isolation is a planned architecture, not yet an operational feature.

The application is still using the original Prisma schema and shared database for its current working functionality.

We must migrate carefully without breaking the existing exam portal.

# 10. Phase 2D — Database Configuration

We added the database configuration editing interface.

Files involved:

- `src/app/super-master/tenants/[id]/DatabaseConfigClient.tsx`
- `src/app/super-master/tenants/[id]/config-actions.ts`
- `src/lib/encryption.ts`

### Database UI

We implemented:
- PostgreSQL provider selection.
- Connection URL input.
- Hidden connection URL by default.
- Eye and eye-off visibility toggle.
- Test Connection.
- Save Configuration.
- Cancel.

### Connection testing

The implementation uses PostgreSQL Pool.

It attempts an actual connection using `pool.connect()` and closes the pool in a `finally` block.

Connection error messages are sanitized.

### Credential encryption

We implemented AES-256-GCM encryption.

Encryption requires:

`ENCRYPTION_KEY`

The key must be 64 hexadecimal characters, representing 32 bytes.

Encrypted credentials use an IV, authentication tag and ciphertext.

Connection URLs must never be logged or exposed in normal UI responses.

### Important unresolved issue

The database configuration schema migration is still required.

The proposed Tenant fields are:

- `databaseProvider`
- `databaseCredentials`
- `dbLastTestedAt`
- `dbTestStatus`
- `dbTestResult`

These fields need to be verified against the actual Prisma schema before migration.

The save operation cannot be considered complete until:
1. The migration is safely created.
2. The migration is applied to the correct database.
3. The application can save encrypted credentials.
4. The application can retrieve and decrypt them server-side.
5. The test connection works.
6. Credentials remain masked in the UI.

**Do not run migrations or `db push` without reviewing the schema and getting approval.**

### Environment configuration

The terminal showed:

`ENCRYPTION_KEY environment variable is required for credential encryption.`

Therefore, the encryption key has not yet been configured in the local environment.

This is the known reason the database save operation failed.
